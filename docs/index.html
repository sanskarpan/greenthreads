Internals

Fiber lifecycle and state machine

Each fiber is a real Go goroutine controlled by the scheduler. The runtime manages transitions between six discrete states.

Created The fiber struct is allocated and Spawn() has been called, but the goroutine has not started executing the fiber function yet.
Runnable The fiber is enqueued in the active scheduler. It is waiting for an available worker slot to execute.
Running A worker goroutine has dequeued the fiber and is actively executing fiber.fn. The fiber holds one worker slot.
Blocked The fiber called FiberMutex.Lock, FiberChannel.Receive, or similar. It is suspended in a wait-list, still holding its worker slot, until unblocked.
Panicked The fiber's function panicked. The runtime recovered the panic, recorded the stack trace in the fiber's metadata, and incremented fibers_panicked_total.
Done The fiber returned normally (or panicked and was recovered). Its result, if any, was forwarded to the caller via the result channel. The worker slot is released.

Quick Start

Up and running in minutes

Install the module and schedule your first fiber, or start the visualization server to see it live in the browser.

bash — install 
$ go get github.com/sanskar/greenthreads/internal/runtime
$ go get github.com/sanskar/greenthreads/internal/scheduler
go — FIFO scheduler, spawn and wait 
package main

import (
    "context"
    "fmt"
    "github.com/sanskar/greenthreads/internal/runtime"
    "github.com/sanskar/greenthreads/internal/scheduler"
)

func main() {
    rt := runtime.NewRuntime(scheduler.TypeFIFO, 4)
    if err := rt.Start(); err != nil {
        panic(err)
    }
    defer rt.Stop(context.Background())

    id, err := rt.Spawn(func() {
        fmt.Println("hello from a fiber")
    }, "greeter")
    if err != nil {
        panic(err)
    }
    fmt.Printf("spawned fiber %d\n", id)
}
go — priority scheduler with functional options 
package main

import (
    "context"
    "fmt"
    "github.com/sanskar/greenthreads/internal/runtime"
    "github.com/sanskar/greenthreads/internal/scheduler"
)

func main() {
    rt := runtime.NewRuntimeWithOptions(
        runtime.WithSchedulerType(scheduler.TypePriority),
        runtime.WithNumWorkers(8),
        runtime.WithMaxFibers(1000),
    )
    if err := rt.Start(); err != nil {
        panic(err)
    }
    defer rt.Stop(context.Background())

    // Lower numeric priority = dispatched first.
    // The runtime uses SpawnWithOptions or fiber.Priority field.
    _, _ = rt.Spawn(func() { fmt.Println("critical") }, "critical")
    _, _ = rt.Spawn(func() { fmt.Println("background") }, "background")

    // Anti-starvation aging runs automatically every 100 dequeues.
    // For immediate relief: rt.Scheduler().(*scheduler.PriorityScheduler).AgeAll()
}
go — structured fan-out with error collection 
package main

import (
    "context"
    "fmt"
    "github.com/sanskar/greenthreads/internal/runtime"
    "github.com/sanskar/greenthreads/internal/scheduler"
)

func main() {
    rt := runtime.NewRuntime(scheduler.TypeWorkStealing, 8)
    if err := rt.Start(); err != nil {
        panic(err)
    }
    defer rt.Stop(context.Background())

    sg := rt.NewSpawnGroup()

    for i := 0; i < 10; i++ {
        i := i
        sg.Spawn(func() {
            process(i)
        }, fmt.Sprintf("worker-%d", i))
    }

    // Wait blocks until all 10 fibers complete.
    errs := sg.Wait()
    for _, err := range errs {
        if err != nil {
            fmt.Printf("worker error: %v\n", err)
        }
    }
}

Schedulers

Algorithm deep-dive

All four schedulers implement the same Scheduler interface and can be swapped at construction time with no other code changes.

FIFO
First-In, First-Out
Strict arrival-order dispatch. The simplest and fastest scheduler — choose it for deterministic, ordered pipelines.
Complexity
Enqueue O(1) Dequeue O(1) Allocs 0/op
Implementation
  • Unbounded slice with a head-index pointer — no element shifting on dequeue.
  • Single sync.Mutex guards the queue; low contention under normal load.
  • Compaction runs when the dead-prefix (before head) exceeds 50% of capacity.
Use when
  • Submission order must equal execution order (audit logs, ordered pipelines).
  • All fibers have similar duration and equal importance.
  • You want the lowest possible dispatch overhead in tests or benchmarks.
Avoid when
  • Some fibers are latency-critical — use Priority instead.
  • Workers are unevenly loaded across cores — WorkStealing distributes better.
Avg dispatch (linux/amd64) ~200 ns/op · 0 allocs
RoundRobin
Round-Robin
Cyclic dispatch that gives each fiber an equal opportunity to run. Same overhead as FIFO; use when fairness matters more than strict ordering.
Complexity
Enqueue O(1) Dequeue O(1) Allocs 0/op
Implementation
  • Identical queue structure to FIFO; the difference is semantic — fibers re-enqueue at the tail after each quantum.
  • Current release: no preemptive yield, so a fiber that doesn't block holds its slot until completion. True round-robin preemption requires cooperative yields (planned feature).
Use when
  • All fibers are homogeneous and should receive equal CPU turns.
  • You want FIFO semantics but with an explicit fairness guarantee in the API contract.
Avoid when
  • Fibers have different priorities — use Priority scheduler.
  • Tasks have highly variable durations — WorkStealing rebalances better.
Avg dispatch (linux/amd64) ~210 ns/op · 0 allocs
Priority
Priority Queue with Anti-Starvation
Min-heap dispatch where lower numeric value = higher priority. Built-in aging prevents indefinite deferral of low-priority fibers.
Complexity
Enqueue O(log n) Dequeue O(log n) Allocs 1/op
Implementation
  • Go's container/heap min-heap ordered by fiber.Priority (int). Lower value = dequeued first.
  • Anti-starvation aging: every 100 calls to Next(), the scheduler decrements the priority of every waiting fiber by 1, allowing low-priority fibers to eventually bubble up.
  • AgeAll() provides immediate relief in extreme imbalance scenarios.
Use when
  • Mixed-criticality workloads: API handlers vs background indexers.
  • SLA tiers where latency-critical work must preempt best-effort work in the queue.
Avoid when
  • All fibers have equal importance — FIFO's O(1) overhead is lower.
Avg dispatch (linux/amd64) ~400 ns/op · 1 alloc
WorkStealing
Work-Stealing
Per-worker deques with idle-steal. Maximizes CPU utilization when fibers have uneven durations across workers.
Complexity
Push (own) O(1) Pop (own) O(1) Steal O(n/2)
Implementation
  • Each worker goroutine owns a double-ended queue (deque). Workers push and pop from their own front; idle workers steal from a randomly chosen victim's back.
  • Steal takes half the victim's work in a single lock acquisition to amortize contention.
  • Worker index uses atomic.AddUint64 for lock-free round-robin initial assignment.
Use when
  • CPU-bound fan-out: parallel map over a dataset where individual item durations vary.
  • Pipeline stages with uneven throughput between workers.
Avoid when
  • Single-worker configuration — stealing overhead with no peers to steal from wastes cycles.
  • Strict ordering is required — steal breaks submission order.
Avg dispatch (linux/amd64) ~350 ns/op · 0 allocs
Sync Primitives

Fiber-aware synchronization

Each primitive enqueues the calling fiber in an internal wait-list and suspends it without releasing its worker slot. When the primitive is satisfied, the fiber is re-enqueued in the scheduler.

FiberMutex
Mutual exclusion lock with a fiber-aware wait queue. Lock(f) suspends the fiber in a FIFO waitlist if the lock is held. Unlock() wakes the next waiter.
Protecting shared mutable state accessed by multiple fibers — counters, maps, caches.
FiberRWMutex
Reader/writer lock variant. Multiple fibers can hold a read lock concurrently; a writer waits until all readers release. Readers are also enqueued cooperatively, not blocked on OS primitives.
Read-heavy shared state: configuration stores, in-memory caches, routing tables.
FiberChannel / FiberChannelOf[T]
Buffered or unbuffered channel between fibers. Send(f, v) blocks the sending fiber when the buffer is full; Receive(f) blocks when empty. FiberChannelOf[T] is a generic wrapper providing type-safe access without interface casts.
Producer-consumer pipelines, inter-fiber messaging, streaming results.
FiberWaitGroup
Barrier that blocks a fiber until a counter reaches zero. Add(n) increments the counter; Done() decrements it; Wait(f) suspends the calling fiber until the counter hits zero.
Fan-out coordination: spawn N worker fibers and wait for all to complete before proceeding.
FiberSemaphore
Counting semaphore that limits the number of fibers accessing a resource concurrently. Acquire(f) blocks when the count is zero; Release() wakes the next queued fiber. Initialized with a capacity N.
Database connection pools, rate limiting within the fiber graph, bounded resource access.
SpawnGroup
High-level structured concurrency primitive. Call sg.Spawn(fn, name) to fan out fibers and sg.Wait() to collect all errors. Eliminates the boilerplate of manual WaitGroup + error channel wiring.
Parallel scraping, batch processing, parallel test suites, multi-stage fan-out pipelines.

FAQ

Frequently asked questions

Each fiber is a real Go goroutine — greenthreads does not implement its own stack-switching or assembly-level context switching. The difference is in dispatch control: the runtime decides which fiber runs next according to the configured scheduling policy (FIFO, Priority, etc.), rather than letting the Go scheduler decide freely. This gives you predictable dispatch order, structured fan-out, per-fiber observability, and deadlock detection — none of which are available with plain goroutines.
The general rule: numWorkers > max_simultaneously_blocked_fibers. Each blocked fiber holds its worker slot. If all slots are occupied by fibers waiting on work from fibers that have not yet been dispatched, the runtime deadlocks. For compute-bound workloads with no blocking, runtime.NumCPU() (the default) is a good starting point. For IO-heavy or mutex-heavy workloads, increase workers significantly — values like 2x or 4x CPU count are common. The deadlock detector will surface a slot exhaustion deadlock if it occurs.
Yes, among fibers waiting in the queue. A fiber that is already running is not preempted — greenthreads uses cooperative (non-preemptive) scheduling. A high-priority fiber spawned while all workers are busy will be the first to run when a worker slot becomes free, but it cannot forcibly interrupt a running fiber. For workloads where preemptive priority is required, consider adding explicit yield points (e.g., short time.Sleep(0) or channel operations) in long-running fibers.
First, enable the deadlock detector: rt.DeadlockDetector().SetEnabled(true). The detector periodically scans the wait-graph for cycles and populates GetDeadlocks() with the offending fiber IDs. The most common cause of deadlock in greenthreads is slot exhaustion: all numWorkers slots are held by fibers blocked on primitives that can only be resolved by fibers waiting in the queue. The fix is to increase numWorkers. Also check: are any fibers blocking on time.Sleep or system calls inside a tight queue? Each such fiber holds a slot for the full duration.
Not directly — there is no preemptive cancellation mechanism. SpawnWithTimeout wraps the fiber with a context.Context deadline: the caller unblocks after the timeout, but the inner goroutine continues until it returns naturally. To support cooperative cancellation inside a fiber, pass a context.Context into the fiber function and check ctx.Done() at logical yield points. This is the same pattern used throughout the Go standard library.
The runtime wraps every fiber function in a recover() call. If the fiber panics, the panic value and stack trace are captured in the fiber's metadata, the state transitions to Panicked, the greenthreads_fibers_panicked_total counter is incremented, and the worker slot is released normally. The runtime and other fibers continue running unaffected. You can inspect panicked fibers via rt.GetAllFibers() and check the PanicInfo field.
In this release, RoundRobin does not implement preemptive quantum-based switching. A fiber that does not block runs to completion on its worker, regardless of scheduler type. True round-robin requires cooperative yield points — a feature planned for a future release. Until then, TypeRoundRobin provides the same ordering guarantee as FIFO but with an explicit API contract that signals your intent to treat fibers equally. If you need equal-time scheduling today, use FIFO and ensure fibers yield regularly via blocking primitives or runtime.Gosched().
With a strong GREENTHREADS_AUTH_TOKEN and TLS enabled, yes — but treat it as a debug/observability tool, not a production API.
